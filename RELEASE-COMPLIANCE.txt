Release compliance — 2026-10-16

Source forks are GPL-2.0-only. Preserve upstream notices and LICENSE, and date modifications in changed source files. New contributions and assets follow the same project license except where a preserved third-party notice states otherwise.

Before distributing any EXE, DLL, installer or NuGet package:
1. Archive the exact commits of BOTH forks used for the build, retaining editable assets, project/build files, LICENSE, notices and build instructions. Record SDK version and build/publish command. Pin the paired fork commits in release notes.
2. Supply complete corresponding source for distributed GPL components, including unchanged Gurux NuGet DLLs. The dependency inventory identifies package source commits when declared. Retrieve those sources with required build files and dependencies, verify that they correspond to the shipped binaries, and include them in the release source bundle. A NuGet download, a current upstream branch link, or this inventory alone is not sufficient. Make the source bundle available alongside binary downloads using a GPLv2-compliant distribution method. Do not rely on a third-party source offer without checking its applicability.
3. Ship LICENSE, THIRD-PARTY-NOTICES.txt and the complete licenses directory with the binary. Preserve the original copyright, redistribution and no-warranty notices. For self-contained/runtime-bundled releases include exact runtime notices as well.
4. Preserve the maintainer-confirmed Codex asset provenance in ASSET-PROVENANCE.txt (Director), and investigate any newly identified source or rights questions before a binary release. Do not imply Gurux endorses this fork. Do not publish modified packages under an official Gurux package identity.
5. Inspect the actual release archive, not just the working tree. Verify the source builds and that all notices survive installer/packaging steps. No binary release is authorized by this document.
